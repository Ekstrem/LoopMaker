## Шаблон ADR

```markdown
# ADR-NNN: {Название}

- **Статус:** Предложено | Принято | Отклонено | Заменено
- **Дата:** 2026-11-09            ← замени на реальную дату (YYYY-MM-DD), плейсхолдер гейт не примет
- **Связанные решения:** {ADR-NNN → почему меняется → комплаенс прошлого (§3.3): соответствует/отступает и почему} ← **обязательное поле всегда**; если ADR того же типа нет — писать `— (ADR того же типа нет)`; пусто = ADR не пишется (или идёт владельцу)
- **Заменяет:** {ADR-XXX | —}          ← новое поле: цепочка «кто кого заменил»
- **Владелец решения:** @{роль}        ← кто отвечает за исполнение и пересмотр
- **Бэклог:** {US / задача / инициатор}

## 1. Контекст
{Что решаем, почему сейчас, ограничения, связанные задачи.}

## 2. Варианты решений (минимум 3; плюсы/минусы — исчерпывающие списки, не по одному пункту)

| Аспект | Значение |
|---|---|
| Схема | {диаграмма/кратко} |
| Описание | {особенности, отличие} |
| Плюсы | {все плюсы через `;`, а не один пункт} |

### Вариант C — {имя}

## 3. Выбранное решение
**Вариант {X}** — {обоснование}.

### 3.1 Протокол согласования (по ролям, не «все согласны»)
| Роль | Принял | Отклонил | Воздержался |
|---|---|---|---|
| @AR | ✅ {дата} | | |
| @TL | | | ⚪ |

### 3.2 Обязательства
| Задача / Поручение | Ответственный |
|---|---|
| {BE-xxx / DO-xxx / …} | {роль} |

### 3.3 Комплаенс
| Что | Значение |
```

## Процесс

| Шаг | Что происходит | Кто | Артефакт |
|---|---|---|---|
| 1. Идея | контекст: что, почему, ограничения (2–3 строки) | автор | ADR §1 |
| 2. Проработка | варианты **≥3** (описание / плюсы-минусы / цели) + скоринг | @AR / доменный владелец | ADR §2 |
| 3. Рецензия | достаточно ли вариантов, согласны ли по плюсам/минусам/целям | владельцы архитектуры | комментарии в задаче |
| 4. Принятие | голосование: принял / отклонил / воздержался | владельцы | протокол §3.1 |
| 5. Статус | `Предложено → Принято` (или `Отклонено`) | автор | статус в ADR |
| 6. Обязательства | задачи → в бэклог | @TL / владелец | задачи в `<backlog>/` |
| 7. Комплаенс | условия пересмотра + кто проверяет | автор + ревьюер | ADR §3.3 |
| 8. Информирование | индекс ADL + строка в чат | автор | ADL + chat |

## Принципы

1. **Минимум 3 варианта** — нет решений с одним вариантом.
2. **Протокол по ролям** — «принял/отклонил/воздержался», а не молчаливое «все согласны».
3. **Бизнес — требования, инженеры — «как»**: владелец задаёт цели и приоритеты, технический выбор
   за владельцами архитектуры.
4. **Бюджет комментариев вместо тайминга встреч** (у нас нет встреч — только файлы):
   на каждый вариант — **не больше 2 комментариев от роли**; формат — **презентация вариантов →
   консенсус → риски фиксируются в комплаенсе**. Если после бюджета консенсуса нет — решение уходит
   владельцу зоны, а не в бесконечный тред. Большой объём ADR — вопрос **модерации** (сколько решений
   поднимаем), а не длины обсуждения.
5. **Дробить сложные решения** — несколько систем → несколько ADR.

## Границы (важно, чтобы не смешивать документы)

| Артефакт | Про что | Где живёт |
|---|---|---|
| **ADR** | архитектурное решение проекта («почему так») | проект, `04-architecture/ADL/` |
| **PDR** | решение о процессе петли | `LoopMaker` (после переноса) |
| **Ранбук** | «как сделать» процедуру | проект, `7-deploy/runbooks/` |
| **Черновик (D-xx)** | идея, ещё не решение | `LoopMaker/retro/drafts/` |
