# KB-001: Остановка чат-транспорта петли (2026-11-17)

## Метаданные

- **Дата инцидента:** 2026-11-17 (проявлялось с ~17:00 MSK, разбор до ~20:30)
- **Статус:** частично решено — доставка в сессии работает, пуш в `main` флакает (причина сети DSH не закрыта)
- **Роль:** @LM (LoopMaster)
- **Проект:** XDiary (публичный) + LoopMaker (приватный, плагин `dsh-loopmaker`)

## Симптом

Роли перестали получать сообщения чата. Владелец: «роли не получают сообщения»,
«чат опять не работает», «BE написал DO, но сообщение не доходит».

## Корневые причины (их четыре, не одна)

Порядок по вкладу, каждая подтверждена отдельно.

### 1. Расщепление чата: роли пишут в worktree, бот читает общее дерево

- Роли пишут outbox в свои worktree (`XDiary-<role>/5-tech-backlog/chat/<role>.md`).
- Бот (`dsh-loopmaker`) читает **только** общее дерево (`XDiary/5-tech-backlog/chat/`).
- Строка роли в worktree → бот её не видит → доставки нет.

**Симптом:** BE написал `→ @DO` в `XDiary-be/.../be.md` — DO не получил.
Проверено: в worktree строка есть, в общем дереве — нет.

**Фикс:** фоновая служба `chat_sync.py` (раз в 5 с) переносит новые строки из
worktree'ев в общее дерево (объединение, без дублей). Запускается автозапуском
(Startup-лаунчер `XDiaryChatSync.cmd`).

### 2. Переименование проекта XDairy → XDiary сломало привязку сессий

- В конфиге плагина оставался `project: XDairy` (старое имя).
- Треды ролей переименованы в `XDiary | …`.
- Плагин искал `«XDairy | Architect»` и т.п. → «НЕ НАЙДЕНА» → доставка вставала.

**Фикс:** `project: XDiary`.

### 3. Плагин читает свой конфиг в пакете, а не профильный патч

- Я правил `profiles\desktop\cordis.patch.yml` (профильный), а плагин читает
  **`node_modules\dsh-loopmaker\cordis.patch.yml`** (внутри установленного пакета).
- Поэтому `dr` долго был «нет в roles», а `project` оставался «XDairy», сколько бы
  я ни правил профиль.

**Урок:** у плагина два файла конфига; правки в профильном патче **не влияют** на
плагин. Источник истины — файл внутри `node_modules\dsh-loopmaker\`.

### 4. Сеть до GitHub рвётся у дочерних git-процессов DSH (НЕ троттлинг GitHub)

- Симптомы: `Connection closed by … port 22` (SSH), `OpenSSL SSL_connect:
  SSL_ERROR_SYSCALL` (HTTPS), `Failed sending data to the peer`.
- **Из моего pwsh** и прямой, и прокси-fetch работают (`rc=0`).
- **Из процесса DSH** (дочерний git плагина) — рвётся.
- **GitHub-тариф ни при чём** (проверено): REST API использовано 67/5000, git-операции
  вообще не лимитируются по тарифу.

**Статус:** точный механизм не установлен (предположительно — сетевая песочница
Electron/DSH для дочерних процессов, либо прокси-путь). Смягчено: чтение чата
переведено на локальное (без сети), пуш раз в 15 мин, таймаут git-процесса 30 с.

## Действия (что было сделано)

1. **Доставка отделена от сети.** Плагин читает чат **локально** (`readFile`), а не
   `git show origin/main`. Доставка в сессии идёт без сети.
2. **Доставка — первым, сеть — потом.** Переставлен порядок в цикле опроса: раньше
   зависший `fetch` (сеть) блокировал чтение локала; теперь доставка всегда первая.
3. **Пуш батчем, реже.** `pushIntervalMs` (дефолт 15 мин) вместо пуша на каждый
   проход; `pollMs` 15 с. Сеть дёргается только при пуше.
4. **Таймаут git 30 с.** Зависший git не вешает цикл опроса навсегда.
5. **Служба синхронизации worktree → общее дерево** (`chat_sync.py`, раз в 5 с).
6. **Чистка конфига:** `project: XDiary`, `roles.dr: DTFReviewer` (в правильном файле —
   внутри пакета), remote переведён на HTTPS+токен, прокси прописан в git-конфиг.

## Ошибки и уроки

1. **«Троттлинг GitHub» — не проверенная гипотеза, принятая за факт.** Я списал на
   неё обрывы соединения, не проверив ни rate-limit API, ни то, что из моего pwsh
   сеть работает. Правильно: сначала разделить «моё окружение работает / окружение
   DSH нет», потом искать причину. **Гипотеза ≠ диагноз.**
2. **Правил не тот файл конфига.** Профильный `cordis.patch.yml` ≠ конфиг внутри
   пакета. Нужно было сразу найти, какой файл реально читает плагин.
3. **Сузил проблему до чат-бота, не увидел системность.** Если сеть рвётся у процесса
   DSH — это бьёт по **всем** агентам (пуш/фетч), а не только по чату. Владелец это
   указал; я должен был сам расширить охват.
4. **Переименование проекта — скрытая миграция.** Смена `project` в конфиге должна
   сопровождаться проверкой привязки всех сессий, а не «починю по ходу».

## Открытые вопросы

- Точная причина обрыва сети у дочерних git-процессов DSH (Electron-песочница?
  прокси?). Проверить: убрать прокси из git-цепочки бота → прямой доступ.
- Тред `po` назван не `XDiary | PO` — доставка PO не работает, ждёт точного названия.
- `fe.md` снова раздут (13183 строк / 45 уникальных) — почистить дедупом после
  стабилизации пуша.
- Токен в remote URL (`https://ghp_…@github.com/…`) светится в process list —
  убрать в credential helper и ротировать токен.
