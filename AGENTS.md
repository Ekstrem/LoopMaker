# AGENTS.md — LoopMaker

Петля — это замкнутый цикл работы, который живёт **в git**, а не в переписке:
задача лежит файлом → роль-агент её берёт → отчитывается в своём файле чата → координатор
проверяет → владелец закрывает. Между шагами не нужно ничего пересылать руками.

Здесь — выжимка рабочей петли из проекта XDiary (6 ролей, 40 задач, два бэклога,
чат без конфликтов) в переносимом виде: правила, форматы, шаблоны и четыре скрипта.

> Этот файл DSH подхватывает автоматически. Если вы агент — сначала прочитайте §1–§5,
> потом `loop.config.json` (§8): там зоны ролей именно для этого проекта.

---

## 1. Пять сущностей петли

| Сущность | Что это | Где живёт |
|---|---|---|
| **Роль** | отдельный тред агента со своей задачей и своей памятью | DSH (1 тред = 1 роль) |
| **Зона** | папки, куда роль имеет право писать | `loop.config.json` |
| **Задача** | карточка `.md` с ID, критериями и статусом | `<backlog>/<роль>/XX-001.md` |
| **Чат** | по файлу на роль (outbox), один писатель на файл | `<backlog>/chat/<роль>.md` |
| **Проверка** | координатор верифицирует, владелец закрывает | чат + поле `Статус:` |

Петля замыкается, когда все пять на месте. Если убрать любую — появится ручная пересылка
сообщений, и это перестанет быть петлёй.

## 2. Роли и зоны

Правило, которое проверено на практике: **у роли ровно одна «своя» папка (ядро)** плюс
узкий служебный набор.

```jsonc
// loop.config.json
"zones": {
  "po": { "core": ["01-product/*"],            "service": ["5-backlog/chat/po.md"] },
  "be": { "core": ["6-code/*"],                "service": ["0-issues/*", "5-backlog/back-end/*", "5-backlog/chat/be.md"] },
  "te": { "core": ["9-tests/*"],               "service": ["5-backlog/tester/*", "5-backlog/chat/te.md"] }
}
```

- **ядро** — то, что вы задаёте как ограничение роли (PO → продукт, BE → код, TE → тесты);
- **служебное** — своя папка задач и свой outbox. Без этого роль не может закрыть задачу
  и ответить в чате, то есть петля не работает;
- **координатор** (обычно `tl`) — видит все папки задач, но не чужие outbox'ы;
- **общие файлы** (`README.md`, `CHANGELOG.md`) — править можно только свои разделы.

**Выход за зону не делаем молча.** Нужен файл в чужой папке — строка в свой outbox
`→ @TL`, координатор создаёт задачу владельцу. Исключение — прямая просьба человека.

## 3. Задачи

Один файл = одна задача. ID с префиксом роли: `BE-001`, `TE-004`, `DO-009`.
Обязательный скелет — в `templates/task.md`.

```markdown
# BE-001: Скаффолд сервиса

- **Статус:** Открыта
- **Приоритет:** P0
- **Источник:** ADR-002, BC-Journal        ← трассировка: откуда взялась
- **Зависимости:** —

## Задача
## Критерии приёмки
- [ ] …
## Результат
```

**Статусы — ровно пять и без синонимов:** `Открыта` → `В работе` → `На проверке` →
`Закрыта` (или `Отклонена`). По полю `Статус:` работают скрипты (`tools/stats.py`,
синк с GitHub Issues), поэтому «Выполнена», «Готово», «Done» ломают автоматику.

**Ритуал закрытия (5 шагов):**
1. исполнитель сделал работу → `На проверке` + строка в чат;
2. координатор проверил по коду/CI → «проверено, можно закрывать»;
3. **статус `Закрыта` ставит владелец задачи**, не координатор;
4. критерии не выполнены → задача не закрывается, формулируется дефект (новая задача);
5. закрытие = критерии + CI зелёный + 1–2 строки в `## Результат` (что и где сделано).

Почему п.3 важен: когда координатор закрывал чужие задачи, в истории появились коммиты
«откат закрытия чужих задач — закрывают владельцы». Владелец знает, что реально сделано.

## 4. Чат (outbox-модель)

Один файл на роль, поэтому одновременная запись в один файл невозможна — merge-конфликтов
нет по конструкции.

```
<backlog>/chat/
  be.md  do.md  fe.md  te.md  ar.md  tl.md  po.md    ← каждый пишет только в свой
  _dialogue.md                                      ← авто-сводка (в .gitignore)
```

Формат строки (иначе авто-сводка её не увидит):

```
- [2026-10-30 18:10] → @DO: нужен URL шлюза для интеграционного теста
```

Правила:
1. пишешь только в свой outbox; читаешь **все** и берёшь адресованное `@<ты>`;
2. одна строка = одно сообщение (многострочные выпадают из сводки);
3. блокер → `@TL`; вопрос по продукту → `@PO`;
4. координатор раз в раунд читает все outbox'ы и эскалирует неотвеченные:
   `python tools/chat_inbox.py` (код 1, если есть вопрос без ответа);
   сводка целиком — `python tools/merge_chat.py`;
5. файлы чата сохраняем в **UTF-8 без BOM** — BOM в начале первой строки ломает
   распознавание сообщения (скрипты его терпят, но чужие редакторы — не всегда).

## 5. Треды в DSH

- **Один тред = одна роль**, заголовок `Проект | Роль`. Так видно, кто чем занят.
- Два способа завести роль:
  - **ветка (fork)** базового треда — роль наследует историю проектирования
    (нужно PO/архитектору/тимлиду); дороже по контексту;
  - **чистый старт** с коротким вводным сообщением — дешевле (нужно исполнителям:
    «твои задачи тут, материалы там, проверяй раз в час»).
- **«Раз в час» — не таймер.** DSH не будит тред по расписанию: агент проверит бэклог,
  когда тред активен. Настоящие часы — GitHub Actions или внешний планировщик.
- Тред изнашивается: когда агент начинает повторяться — архивируйте и заведите новый,
  одним вводным сообщением (в XDiary так переезжали BackEnd и TechLead).

## 6. Насколько это жёстко

| Механизм | Ловит? | Стоимость |
|---|---|---|
| Промпт роли («пиши только в X») | мягко, на послушании | 0 |
| `AGENTS.md` в корне проекта и в папке роли | мягко, но в каждом запросе | 5 минут |
| `tools/check_paths.py` в CI (префиксы коммитов) | постфактум, зато громко | полчаса |
| PR + branch protection + required checks | жёстко, блокирует | час + трение |
| Отдельный воркспейс на папку роли | физически (песочница) | рвёт цикл: статус задачи не закрыть |

Практика XDiary: промпт + `AGENTS.md` + guard дают 0 ложных срабатываний на 56 коммитах
и ловят реальные вылеты (тестер, правивший код сервиса). Строгий режим «только ядро»
даёт 21 нарушение — из них 20 это штатные «закрыл задачу / написал в чат», поэтому
ядро + служебное — правильный дефолт.

## 7. Автоматика, которую стоит завести

| Workflow | Триггер | Делает |
|---|---|---|
| `merge-chat.yml` | push при изменении `chat/*.md` | `tools/merge_chat.py` → сводка (артефакт) |
| `guard-paths.yml` | push в `main` | `tools/check_paths.py` — роль не вышла за зону |
| `stats.yml` | push при изменении задач/README | `tools/stats.py --check` — README не отстал |
| `sync-board.yml` | push в `main` | задачи `.md` → GitHub Issues + Projects |
| `ci-*.yml` | push по путям сервиса | сборка/тесты/Docker-образ |

Важно: сводку чата **не коммитим** (`.gitignore`), её собирают локально
(`python tools/merge_chat.py`) или берут из артефакта Actions — иначе получите
конфликт «сгенерированный файл против ручных правок».

## 8. Как завести петлю в новом проекте

1. Скопировать в репозиторий: `AGENTS.md`, `loop.config.json`, `tools/`, `templates/`.
2. В `loop.config.json` прописать свои зоны: роли → `core`/`service`, папку бэклога,
   порядок ролей для статистики.
3. Создать каркас папок: `01-product`, `02-cjm`, …, `5-backlog/{<роли>}`, `5-backlog/chat`,
   `5-backlog/chat/README.md` (правила чата) и пустые `<роль>.md`.
4. Положить `templates/AGENTS.zone.md` в каждую папку-зону (короткий локальный запрет).
5. Разбить работу на задачи по `templates/task.md`, разложить по папкам ролей.
6. Завести треды: по одному на роль, заголовок `Проект | Роль`, вводное сообщение —
   зона, папка задач, формат чата, критерий готовности.
7. Включить guard: `python tools/check_paths.py --zones` (карта) и workflow из §7.
8. Договориться о префиксах коммитов (`be:`, `fe:`, `do:`, `te:`, `ar:`, `tl:`, `po:`),
   иначе guard не сможет определить роль и будет всё пропускать.
9. Прогнать `python tools/stats.py --write` и вставить маркеры в README.
10. Проверить цикл на одной задаче: создать → взять → `На проверке` → верификация →
    `Закрыта`. Если что-то пришлось передавать руками — вернуться к §1 и найти пропуск.

## 9. Антипаттерны (все — из реальных грабель)

- **Один общий файл чата** — конфликты и потерянные сообщения. Только outbox.
- **Синонимы статусов** — «Выполнена» против «Закрыта»: статистика и синк расходятся.
- **Ручная таблица статистики** — отстаёт на первой же неделе (в XDiary: 32/8 против 35/5).
- **Координатор закрывает чужие задачи** — теряется смысл «владелец проверил сам».
- **Секреты в промпте** — пароли и ключи остаются в транскриптах тредов и в git.
- **Роли без префиксов коммитов** — guard всё пропускает, забор не работает.
- **«Проверяй раз в час» как таймер** — никто не придёт, пока тред не активен.
- **Коммит сводки чата в git** — правки перетираются генератором.

## 11. Плагин `dsh-loopmaker` (этот же репозиторий)

Корень репозитория — ещё и пакет DSH-плагина: он читает outbox-чат и **доставляет**
сообщения адресатам в их сессии, то есть роль просыпается без ручного переключения треда.

- подробности, установка и параметры — [PLUGIN.md](PLUGIN.md);
- код: `lib/parse.js` (формат строки), `lib/bridge.js` (маршрутизация, батчинг, лимиты),
  `lib/state.js` (что доставлено, цели ролей, история для счёта кругов),
  `lib/sessions.js` (поиск сессии по заголовку + ретаргет при архивации);
- тесты: `npm test` (35 тестов, DSH не нужен).

**Адресат перепроверяется перед отправкой:** если тред роли уехал в архив, мост сам
переключается на живой с тем же именем (лог `таргет переехал`), а не пишет в архив.
**Порог против пинг-понга:** 4 круга на пару за 30 минут или 40 реплик на роль за час →
переписка уходит координатору (`escalateTo`, по умолчанию TechLead), пара замораживается
на час. Координатор сам решает: техническое — себе, бизнесовое — PO, архитектурное — AR.

**Правило для агентов:** формат строки чата — общий контракт. Меняешь его
(стрелку, тег адресата, время) — правь одновременно `lib/parse.js`,
`tools/merge_chat.py`, `tools/chat_inbox.py` и тесты, иначе одно из трёх перестанет
видеть сообщения. Так уже случалось: BOM и `@TESTENGINEER` вместо `@TE` ломали
распознавание молча.
