# AGENTS.md — LoopMaker

Петля — это замкнутый цикл работы, который живёт **в git**, а не в переписке:
задача лежит файлом → роль-агент её берёт → отчитывается в своём файле чата → координатор
проверяет → владелец закрывает. Между шагами не нужно ничего пересылать руками.

Здесь — выжимка рабочей петли из проекта XDiary (6 ролей, 40 задач, два бэклога,
чат без конфликтов) в переносимом виде: правила, форматы, шаблоны и четырнадцать скриптов.

> Этот файл DSH подхватывает автоматически. Если вы агент — сначала прочитайте §1–§5,
> потом `loop.config.json` (§8): там зоны ролей именно для этого проекта.

---

## 1. Пять сущностей петли

| Сущность | Что это | Где живёт |
|---|---|---|
| **Роль** | отдельный тред агента со своей задачей и своей памятью | DSH (1 тред = 1 роль) |
| **Зона** | папки, куда роль имеет право писать | `loop.config.json` |
| **Задача** | карточка `.md` с ID, критериями и статусом | `<backlog>/<роль>/XX-001.md` |
| **Чат** | по файлу на роль (outbox), один писатель на файл | `<backlog>/chat/<роль>.md` |
| **Проверка** | координатор верифицирует, владелец закрывает | чат + поле `Статус:` |

Петля замыкается, когда все пять на месте. Если убрать любую — появится ручная пересылка
сообщений, и это перестанет быть петлёй.

## 2. Роли и зоны

Правило, которое проверено на практике: **у роли ровно одна «своя» папка (ядро)** плюс
узкий служебный набор.

```jsonc
// loop.config.json
"zones": {
  "po": { "core": ["01-product/*"],            "service": ["5-backlog/chat/po.md"] },
  "be": { "core": ["6-code/*"],                "service": ["0-issues/*", "5-backlog/back-end/*", "5-backlog/chat/be.md"] },
  "te": { "core": ["9-tests/*"],               "service": ["5-backlog/tester/*", "5-backlog/chat/te.md"] }
}
```

- **ядро** — то, что вы задаёте как ограничение роли (PO → продукт, BE → код, TE → тесты);
- **служебное** — своя папка задач и свой outbox. Без этого роль не может закрыть задачу
  и ответить в чате, то есть петля не работает;
- **координатор** (обычно `tl`) — видит все папки задач, но не чужие outbox'ы;
- **процессная роль** (LoopMaster / `@LM`) — правила, линтеры, миграции статусов,
  `AGENTS.md`/`STATUSES.md`, шаблоны; ей адресуют **только процессные вопросы**
  (статусы задач и прогонов — не её зона, владелец попросил не дублировать);
- **общие файлы** (`README.md`, `CHANGELOG.md`) — править можно только свои разделы.

**Выход за зону не делаем молча.** Нужен файл в чужой папке — строка в свой outbox
`→ @TL`, координатор создаёт задачу владельцу. Исключение — прямая просьба человека.

## 3. Задачи

Один файл = одна задача. ID с префиксом роли: `BE-001`, `TE-004`, `DO-009`.
Обязательный скелет — в `templates/task.md`.

```markdown
# BE-001: Скаффолд сервиса

- **Статус:** ToDo
- **Приоритет:** P0
- **Источник:** ADR-002, BC-Journal        ← трассировка: откуда взялась
- **Зависимости:** —
- **Прорабатывает:** @AR                  ← только для «На проработке»
- **В работе с:** 2026-11-05               ← только для «В работе»
- **Проверяет:** @TL + коммит/CI          ← только для «На проверке»
- **Пауза:** причина · **Разблокирует:** @DO/доступ · **До:** дата   ← только «В паузе»

## Задача
## Критерии приёмки
- [ ] …
## Результат
```

**Статусы — восемь, без синонимов** (схема, матрица переходов и обязательные поля —
в [STATUSES.md](STATUSES.md)):

```
Идея → На проработке → ToDo → В работе → На проверке → Закрыта
                        ↑         ↓
                        └── В паузе        (+ Отклонена)
```

`На проработке` — активное состояние с назначенным проработчиком (например Arch
проверяет идею BE на соответствие ADR). `В паузе` — осознанная остановка: обязательны
`Пауза:` и `Разблокирует:`, иначе пауза ничего не сообщает. `ToDo` — проработано;
`Идея → ToDo` напрямую разрешено, если проработка не нужна.

По полю `Статус:` работают `tools/stats.py`, `tools/sweep.py`, `tools/status_lint.py`,
синк с GitHub Issues — поэтому «Открыта», «Выполнена», «Готово», «Done», «Пауза»
ломают автоматику (линтер ловит их отдельно, с подсказкой).

**Ритуал закрытия (5 шагов):**
1. исполнитель сделал работу → `На проверке` + строка в чат;
2. ревьюер домена (@AR архитектура, @DO инфра, @PO продукт, @TL остальное) проверил по коду/CI → «проверено, можно закрывать»; спор двух ревьюеров решает @TL;
3. **статус `Закрыта` ставит владелец задачи**, не координатор;
4. критерии не выполнены → задача не закрывается, формулируется дефект (новая задача);
5. закрытие = критерии + CI зелёный + 1–2 строки в `## Результат` (что и где сделано).

Почему п.3 важен: когда координатор закрывал чужие задачи, в истории появились коммиты
«откат закрытия чужих задач — закрывают владельцы». Владелец знает, что реально сделано.

## 4. Чат (outbox-модель)

Один файл на роль, поэтому одновременная запись в один файл невозможна — merge-конфликтов
нет по конструкции.

```
<backlog>/chat/
  be.md  do.md  fe.md  te.md  ar.md  tl.md  po.md    ← каждый пишет только в свой
  _dialogue.md                                      ← авто-сводка (в .gitignore)
```

Формат строки:

```
- [2026-10-30 18:10] → @DO: нужен URL шлюза для интеграционного теста
```

Канон — со скобками и один адресат; парсер (`lib/parse.js`) дополнительно понимает
строки **без скобок** (`- 2026-11-01 17:19 → @TL: …`, таких было 88) и **несколько
адресатов** через `+` (`@DO + @TE`) — доставляется каждому. Оба отклонения раньше
терялись молча, поэтому есть линтер `tools/chat_lint.py`: он находит нераспознанные
строки и пишет автору замечание в `chat/_lint.md`, откуда мост доставляет его в
сессию автора.

Правила:
1. пишешь только в свой outbox; читаешь **все** и берёшь адресованное `@<ты>`;
2. одна строка = одно сообщение (многострочные выпадают из сводки);
3. блокер → `@TL`; вопрос по продукту → `@PO`;
4. координатор раз в раунд читает все outbox'ы и эскалирует неотвеченные:
   `python tools/chat_inbox.py` (код 1, если есть вопрос без ответа);
   сводка целиком — `python tools/merge_chat.py`;
5. файлы чата сохраняем в **UTF-8 без BOM** — BOM в начале первой строки ломает
   распознавание сообщения (скрипты его терпят, но чужие редакторы — не всегда).
6. **в чат не попадают секреты и их фрагменты.** Чат коммитится, репозиторий часто
   публичный: вставленный ключ остаётся в истории навсегда. Сравнивать секреты —
   `python tools/keycmp.py --a-env A --b-env B` (печатает «совпадают/нет» + отпечаток,
   без значений). Проверка: `python tools/check_secrets.py`, job `guard-secrets` (§7),
   правила — §13.

## 5. Треды в DSH

- **Один тред = одна роль**, заголовок `Проект | Роль`. Так видно, кто чем занят.
- Два способа завести роль:
  - **ветка (fork)** базового треда — роль наследует историю проектирования
    (нужно PO/архитектору/тимлиду); дороже по контексту;
  - **чистый старт** с коротким вводным сообщением — дешевле (нужно исполнителям:
    «твои задачи тут, материалы там, проверяй раз в час»).
- **«Раз в час» — не таймер.** DSH не будит тред по расписанию: агент проверит бэклог,
  когда тред активен. Настоящие часы — GitHub Actions или внешний планировщик.
- Тред изнашивается: когда агент начинает повторяться — архивируйте и заведите новый,
  одним вводным сообщением (в XDiary так переезжали BackEnd и TechLead).

## 6. Насколько это жёстко

| Механизм | Ловит? | Стоимость |
|---|---|---|
| Промпт роли («пиши только в X») | мягко, на послушании | 0 |
| `AGENTS.md` в корне проекта и в папке роли | мягко, но в каждом запросе | 5 минут |
| `tools/check_paths.py` в CI (префиксы коммитов) | постфактум, зато громко | полчаса |
| PR + branch protection + required checks | жёстко, блокирует | час + трение |
| Отдельный воркспейс на папку роли | физически (песочница) | рвёт цикл: статус задачи не закрыть |

Практика XDiary: промпт + `AGENTS.md` + guard дают 0 ложных срабатываний на 56 коммитах
и ловят реальные вылеты (тестер, правивший код сервиса). Строгий режим «только ядро»
даёт 21 нарушение — из них 20 это штатные «закрыл задачу / написал в чат», поэтому
ядро + служебное — правильный дефолт.

## 7. Автоматика, которую стоит завести

| Workflow | Триггер | Делает |
|---|---|---|
| `merge-chat.yml` | push при изменении `chat/*.md` | `tools/merge_chat.py` → сводка (артефакт) |
| `guard-paths.yml` | push в `main` | `tools/check_paths.py` — роль не вышла за зону |
| `stats.yml` | push при изменении задач/README | `tools/stats.py --check` — README не отстал |
| `sweep.yml` | `schedule` (раз в час) + `workflow_dispatch` | `tools/sweep.py` — что стоит без движения и где «обещано, но не начато» → issue-сигнал (и закрывает его, когда чисто) |
| `guard-secrets.yml` | push в `main` + `workflow_dispatch` | `tools/check_secrets.py` — секреты и их **фрагменты** в чате/задачах/доках; код 1 на находке |
| `chat-guards.yml` | push **только** по `<backlog>/chat/**` | лёгкие guard'ы чата (линт формата + линт статусов + секреты); тяжёлые джобы на переписку не запускаются |
| `sync-board.yml` | push по `<backlog>/**` **без** `chat/**` | задачи `.md` → GitHub Issues + Projects |
| `health.yml` | `schedule` (раз в сутки) + `workflow_dispatch` | `tools/health.py` → `HEALTH.md` + `health/history.jsonl` (дашборд, не гейт) |
| `guard-tools.yml` | push по `tools/**` | `tools/sync_tools.py --check` — копия инструмента не расходится с манифестом `tools/.sources.json` |
| `ci-*.yml` | push по путям сервиса | сборка/тесты/Docker-образ |

Важно: сводку чата **не коммитим** (`.gitignore`), её собирают локально
(`python tools/merge_chat.py`) или берут из артефакта Actions — иначе получите
конфликт «сгенерированный файл против ручных правок».

## 8. Как завести петлю в новом проекте

1. Скопировать в репозиторий: `AGENTS.md`, `loop.config.json`, `tools/`, `templates/`.
2. В `loop.config.json` прописать свои зоны: роли → `core`/`service`, папку бэклога,
   порядок ролей для статистики.
3. Создать каркас папок: `01-product`, `02-cjm`, …, `5-backlog/{<роли>}`, `5-backlog/chat`,
   `5-backlog/chat/README.md` (правила чата) и пустые `<роль>.md`.
4. Положить `templates/AGENTS.zone.md` в каждую папку-зону (короткий локальный запрет).
5. Разбить работу на задачи по `templates/task.md`, разложить по папкам ролей.
6. Завести треды: по одному на роль, заголовок `Проект | Роль`, вводное сообщение —
   зона, папка задач, формат чата, критерий готовности.
7. Включить guard: `python tools/check_paths.py --zones` (карта) и workflow из §7.
8. Договориться о префиксах коммитов (`be:`, `fe:`, `do:`, `te:`, `ar:`, `tl:`, `po:`),
   иначе guard не сможет определить роль и будет всё пропускать.
9. Прогнать `python tools/stats.py --write` и вставить маркеры в README.
10. Проверить цикл на одной задаче: создать → взять → `На проверке` → верификация →
    `Закрыта`. Если что-то пришлось передавать руками — вернуться к §1 и найти пропуск.

## 9. Антипаттерны (все — из реальных грабель)

- **Один общий файл чата** — конфликты и потерянные сообщения. Только outbox.
- **Синонимы статусов** — «Выполнена» против «Закрыта»: статистика и синк расходятся.
- **Ручная таблица статистики** — отстаёт на первой же неделе (в XDiary: 32/8 против 35/5).
- **Координатор закрывает чужие задачи** — теряется смысл «владелец проверил сам».
- **Секреты в промпте** — пароли и ключи остаются в транскриптах тредов и в git.
- **Роли без префиксов коммитов** — guard всё пропускает, забор не работает.
- **«Проверяй раз в час» как таймер** — никто не придёт, пока тред не активен.
- **Секрет в чате — и особенно фрагмент секрета «чтобы сравнить».** В XDiary так утекли
  хвосты `Jwt:SigningKey` (03.11), а потом те же фрагменты попали в **сообщение о самом
  инциденте** (04.11): объяснять «что было» естественнее, чем промолчать. Липнут оба.
- **Коммит сводки чата в git** — правки перетираются генератором.

## 10. Что копировать, а что писать своё

| Копировать как есть | Писать под проект |
|---|---|
| `tools/check_paths.py`, `tools/stats.py`, `tools/merge_chat.py`, `tools/chat_inbox.py`, `tools/sweep.py`, `tools/check_secrets.py`, `tools/keycmp.py`, `tools/chat_lint.py`, `tools/check_workflow_paths.py`, `tools/ci_metrics.py`, `tools/status_lint.py`, `tools/migrate_statuses.py`, `tools/health.py`, `tools/sync_tools.py` | `loop.config.json` (зоны, папки, роли, статусы) |
| форматы задачи и строки чата | состав ролей и их компетенции |
| ритуал проверки и закрытия | домен: что считается «готово» |
| workflow-файлы | CI-специфика (язык, тесты, деплой) |

**Копии инструментов не расходятся молча.** Проект не может чекаутить приватный
LoopMaker в CI, поэтому инструменты копируются. Чтобы копия не «уехала» от шаблона:

```bash
python tools/sync_tools.py --check          # CI: копии совпадают с манифестом
python tools/sync_tools.py --report         # чем копии отличаются от ../LoopMaker
python tools/sync_tools.py --pull --from ../LoopMaker   # пересинхронизировать
```

Манифест — `tools/.sources.json` (sha256 тела каждого общего скрипта на момент синка).
Правил копию руками — обновишь манифест тем же коммитом, иначе `guard-tools.yml` покраснеет.

## 11. Плагин `dsh-loopmaker` (этот же репозиторий)

Корень репозитория — ещё и пакет DSH-плагина: он читает outbox-чат и **доставляет**
сообщения адресатам в их сессии, то есть роль просыпается без ручного переключения треда.

- подробности, установка и параметры — [PLUGIN.md](PLUGIN.md);
- код: `lib/parse.js` (формат строки), `lib/bridge.js` (маршрутизация, батчинг, лимиты),
  `lib/state.js` (что доставлено, цели ролей, история для счёта кругов),
  `lib/sessions.js` (поиск сессии по заголовку + ретаргет при архивации);
- тесты: `npm test` (59 тестов, DSH не нужен).

**Адресат перепроверяется перед отправкой:** если тред роли уехал в архив, мост сам
переключается на живой с тем же именем (лог `таргет переехал`), а не пишет в архив.
**Порог против пинг-понга:** 4 круга на пару за 30 минут или 40 реплик на роль за час →
переписка уходит координатору (`escalateTo`, по умолчанию TechLead), пара замораживается
на час. Координатор сам решает: техническое — себе, бизнесовое — PO, архитектурное — AR.

**Правило для агентов:** формат строки чата — общий контракт. Меняешь его
(стрелку, тег адресата, время) — правь одновременно `lib/parse.js`,
`tools/merge_chat.py`, `tools/chat_inbox.py` и тесты, иначе одно из трёх перестанет
видеть сообщения. Так уже случалось: BOM и `@TESTENGINEER` вместо `@TE` ломали
распознавание молча.

## 12. Намерение ≠ действие

Самый частый сбой петли — не грубая ошибка, а **пустой ход**: агент пишет «беру TE-015,
потом TE-016…», заканчивает ход без единого tool call, файлы не меняются, а со стороны
выглядит, будто работа идёт. В XDiary это случилось на TE-015 (01.11): пять минут
разговоров вместо коммита, пока человек не пнул.

Правила, которые это лечат:

1. **Первый шаг по задаче — два артефакта:** `Статус: В работе` в файле задачи и строка
   в свой outbox. Потом код. Если ход оборвётся, задача уже помечена «в работе» и
   попадёт в обход, а не потеряется.
2. **Ход нельзя заканчивать обещанием.** Либо tool call в этом же ходе, либо явное
   «жду: <чего именно>» (CI, approval, решение, файл).
3. **Прогресс = артефакт:** коммит, изменённый `Статус:`, строка в чате. Самоотчёт
   («сделано», «пушнул», «жду CI») без ссылки на коммит не проверяется и не считается.
4. **Не спрашивать «почему остановился».** Это приглашает оправдание («не остановился»).
   Факт: «в прошлом ходе не было tool call — продолжай с шага N».
5. **Размер шага:** одна задача = один ход = один коммит. Очередь из семи задач,
   объявленная в одном сообщении, в ход не влезет — модель остановится на первой фразе.
6. **Прогресс проверяется в origin.** «Проверено» = `git show origin/main:<файл>` или ссылка на run/PR, а не «у меня в дереве так»:
   дерево общее, незакоммиченное может исчезнуть (XDiary, 06.11).

Детектор: `python tools/sweep.py --config loop.config.json` — секция «обещано, но не
начато» (в чате есть «беру XX-001», а статус задачи всё ещё `Открыта`).

## 13. Секреты в петле

Чат и задачи — текстовые файлы в git, а репозиторий часто публичный. Секрет, попавший
сюда, остаётся в истории навсегда: убрать можно только force-push'ем, который ломает
клоны у всех. Поэтому правило не «будь осторожен», а механическое.

**Три инструкции:**
1. Значения и их **фрагменты** — только в `.env` / GitHub Secrets / Secrets стенда.
   Не в чат, не в задачи, не в README, не в коммиты. «Хвост для сравнения» — тоже секрет.
2. Сравнивать секреты — `python tools/keycmp.py --a-env A --b-env B`. Печатает
   «совпадают / НЕ совпадают» и первые 8 символов sha256, значения не выводит.
3. Инцидент описываем без цитат: «ключи различаются», «фрагменты скрыты» — не
   «он заканчивается на …». Второй реальный заход был именно такой: сообщение
   о первом инциденте само процитировало хвосты.

**Гейты:** `tools/check_secrets.py` + `templates/guard-secrets.yml`. В CI — режим
`--range BASE..HEAD` (сканируется только то, что пушится, включая уже зачищенные
в рабочем дереве строки), локально — без `--range` по всему обходу.
Два класса правил: `assign` (имя ключа + значение — ловит фрагменты) и `shape`
(base64/hex/JWT/`ghp_`/`AKIA`/TG-бот/PEM), плюс `fragment-ellipsis` под обрезанные хвосты.

**Чего линтер не поймёт:** описание словами («ключ начинается на X»), одно-двухсимвольные
фрагменты, секрет, разложенный по строкам. Это закрывает только инструкция 1 и человек.

**Процедура при утечке:**
1. зачистить строку в рабочем файле (в своём outbox — своей правкой);
2. **ротация** секрета: координатор поручает владельцу (GitHub Secrets + `.env` на стендах);
3. историю git не переписывать — ротация дешевле force-push;
4. запись в `CHANGELOG` проекта + строка в свой outbox: «инцидент, значение скрыто».

## 14. CI: отмены, очередь и доказательства

Самая дорогая ошибка в петле с агентами — **отменять прогоны «на всякий случай»**.
В XDiary (DO-023, 05.11) это выглядело так: прогоны отменяли на 1–2-й минуте, а `test`
на деле проходил за **69 с**; в итоге приёмка четырёх задач висела без результата.
Правила, которые это лечат:

1. **Гарантированное окно — 5 минут.** Ни одна роль не отменяет прогон, которому меньше
   5 минут от `started_at`. Исключение — `queued` (ещё не стартовал): это не результат,
   дубликат очереди отменять можно.
2. **`in_progress` отменяется только по факту ≥5 минут без прогресса**, с названной
   причиной: «висит на шаге X, N мин, лог Y». Фраза «долго идёт» — не причина.
3. **Не объявлять прогон зависшим «по ощущению»**: сначала сверить `started_at`,
   `updated_at` и текущий шаг по API. Реальный случай: run'ы назвали зависшими, а они
   уже были `completed/failure`.
4. **Автоотмена новым пушем (`cancel-in-progress`) для тяжёлых джобов запрещена** —
   они идут в очередь. Для лёгких guard'ов (линт, секреты) — наоборот, разрешена.
   **Но очередь не бесконечна:** на группу держится один pending-прогон, и новый пуш
   вытесняет ожидающий — он завершается как `cancelled` без единого шага. Признак
   вытеснения: нет шагов / пустой `started_at`, виноват пушивший. Правило: не пушить
   код, пока по группе висит pending; «cancelled» без шагов ≠ чья-то отмена.
5. **Переписка не триггерит тяжёлое.** Тяжёлые workflow ставят
   `paths-ignore: <backlog>/chat/**`; guard'ы чата живут в отдельном `chat-guards.yml`
   (шаблон — `templates/chat-guards.yml`) со своим `concurrency`. Иначе каждый пуш
   в чат отменяет идущий E2E. Проверка правила механическая:
   `python tools/check_workflow_paths.py` — падает на workflow с `on.push` без
   `paths`/`paths-ignore`; лёгкие исключения перечисляются в `loop.config.json`
   (`ci.light_workflows`).
6. **Отменённый прогон — не доказательство.** Ни зелёный, ни красный: для приёмки нужен
   прогон, завершившийся сам (`success`/`failure`), иначе rerun.
7. **Разделение ролей при разборе:** диагностика CI — владелец инфраструктуры
   (`@DO`): очередь, concurrency, минуты, раннеры. Координатор (`@TL`) читает
   **результат** («зелёный/красный по задаче»), а не диагностирует.
   Пустые аннотации («Process completed with exit code 1» без имени теста) — повод
   открыть лог, а не объявлять причину по памяти.
8. **Цифра вместо ощущения.** Прежде чем говорить «долго», посчитайте:
   `python tools/ci_metrics.py --workflow-path ci-tests.yml` — p50/p95 по успешным
   прогонам. В XDiary это дало `test` p95 ≈ 71 с и `front-e2e` p95 ≈ 157 с при
   пятиминутном окне — то есть отмена почти всегда была ошибкой, а не оптимизацией.
9. **Расширяя `paths-ignore`, переноси guard-джобы, а не выключай.** Урок XDiary
   (DO-031/DO-032): сузили `ci-tests` до чата, а `guard-secrets` для файлов задач не
   появился — задачи почти сутки не сканировались на секреты, и никто не заметил.

## 15. Что спрашивать у владельца, а что — из документов

Прежде чем задать вопрос владельцу, **проверь ADR / канвас / задачу**. Если решение уже
принято в документе — реализуй по нему и проси не решение, а недостающий ресурс.
Переспрашивание принятого решения читается как «мы не проектировали» и сжигает доверие
(реальный прокол в XDiary: спросили «какой канал OTP?», хотя ADR-021 уже фиксировал SMS).

**Решаем сами:** всё, что уже есть в ADR/канвасе/README; технические детали (библиотеки,
структура кода, имена полей); порядок работы над задачами; починку того, что сломано и
мешает — с записью решения в задачу.

**Спрашиваем владельца** (не решаем сами):
- **доступы и ключи** — аккаунт провайдера, бот-токен, домен, платёжные данные: это
  ресурсы, которых у агентов физически нет;
- **продуктовые приоритеты** — что делаем сейчас, что откладываем, что вырезаем;
- **изменение уже принятого решения** (в т.ч. правка ADR) — только с его ведома;
- **изменение правил процесса** — как закрываем задачи, как меряем готовность.

Вопрос формулируется как **запрос ресурса или выбора приоритета**, а не как
«переспросим, чтобы не ошибиться».

## 16. Здоровье петли (дашборд)

Оценки «на глаз» не масштабируются. Дашборд сводит к нескольким числам то, что уже
считают гейты, и делает состояние петли наблюдаемым без чтения чата:

| Метрика | Источник | Норма |
|---|---|---|
| Ошибки статусов | `tools/status_lint.py` | 0 |
| Задачи без движения / «обещано, но не начато» | `tools/sweep.py` | 0 |
| Гигиена гейтов: `stats --check`, `chat_lint --check`, `check_workflow_paths` | те же скрипты | 3/3 |
| CI: худший p95 по тяжёлым джобам | GitHub API (считает сам `health.py`) | < 300 с |
| Вопросы в чате без ответа | `tools/chat_inbox.py` | 0 |
| Копии инструментов разошлись с LoopMaker (если репозиторий рядом) | сравнение `tools/*.py` | 0 |

```bash
python tools/health.py                 # таблица в stdout
python tools/health.py --write         # + HEALTH.md и health/history.jsonl
python tools/health.py --no-ci         # без сети (быстро, локально)
```

Расписание — `templates/health.yml`: раз в сутки, коммитит `HEALTH.md` и
`health/history.jsonl` (в файле же тренд-спарклайны по последним замерам).
Дашборд **не гейт**: он никогда не валит CI и ничего не чинит. Красная строка — повод
открыть задачу, а не повод что-то автоматически менять.

Правило: **новый гейт добавляется в дашборд тем же коммитом**, иначе через месяц никто
не вспомнит, что он существует.

## 17. Git-инцидент: один восстановитель

Решение владельца XDiary (06.11), потому что в общем дереве каждый «чинил по-своему»
и затирал чужое (`autostash`, `rebase`, `checkout -- .`).

- **Признак инцидента:** конфликт `rebase`/`merge`, «cannot autostash», исчезли коммиты
  или правки, ветви разошлись, чужой force-push.
- **STOP — только при потере или повреждении** (конфликт `rebase`/`merge`,
  «cannot autostash», пропавшие коммиты, чужой force-push). Обычный non-fast-forward —
  рутина: `fetch` + `rebase` без force-push, никто не останавливается.
- **STOP объявляет координатор** (обычно `@TL`) одной строкой в чате, с признаком.
- **Роли замирают:** не пушат, не правят дерево, не запускают `reset/checkout/stash/rebase`.
- **Восстанавливает один** — координатор; затем объявляет «работа возвращена» и называет
  коммит, что восстановлено и что потеряно.
- **Историю не переписывать**: force-push запрещён, потерянное делается заново.
- **Урок фиксируется правилом** в тот же день, иначе инцидент повторится.

Почему так: у всех ролей **одно рабочее дерево**. «Помочь» через `git checkout -- .`
означает стереть чужую незакоммиченную работу — что и случилось дважды за день.
