# AN-05. Адресат без `@`: строка есть, доставки нет

| Поле | Значение |
|---|---|
| **Дата** | 2026-11-10 |
| **Нашёл** | @TL (20:05): моя строка `→ te:` не попала в выборку @TE; `chat_lint` дал `rc=0` |
| **Инструмент** | `tools/chat_lint.py` (LoopMaker источник + копия XDiary) |
| **Класс** | линтер «понимает» формат, который мост НЕ доставляет → потеря молча |

## Что случилось

Пилот фильтра писал шаблонный ответ как `- [ts] → te: общение через владельца или на ретро.`
без `@`. Мост (`lib/parse.js`) ищет адресата по `@` — строка не доставлена, адресат её не
увидел. `chat_lint` при этом печатал «формат: N не каноном … **распознаются**» и давал `rc=0`:
линтер и мост расходились в терпимости, и расхождение стоило доставки.

## Фикс

`addr_without_at(line)`: канон-строка, у которой адресат после **первой** стрелки начинается
не с `@` → считаем отдельным счётчиком и печатаем
`::warning::адресат без «@»: N строк — мост их НЕ доставит; канон: → @роль: текст`.
Смотрим только первую стрелку: в тексте сообщений `→` встречается как «следовательно»
(первая версия регекса из-за этого насчитала 4231 ложную строку — поймано проверкой).
Добавлен флаг `--fail-no-at`: с ним такие строки дают `rc=1` (для CI — после разбора
исторических 11 строк).

## Проверка (§5.4)

- норма: `--check` → `rc=0` + предупреждение «адресат без `@`: 11 строк»;
- дефект: `--check --fail-no-at` → `rc=1`;
- `sync_tools --check` — 39/39.

## Вывод

Шаблон фильтра (PDR-041) обязан писаться как `→ @роль:`; в пилоте это проверено отдельно.
