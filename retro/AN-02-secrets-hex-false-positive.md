# AN-02. Дефект гейта: `check_secrets` красит публичные идентификаторы как секреты

| Поле | Значение |
|---|---|
| **Дата** | 2026-11-07 |
| **Нашёл** | @DO/@TL (5 находок), независимо подтвердил @LM |
| **Гейт** | `tools/check_secrets.py` (`hex-long`) |
| **Класс** | ложное срабатывание: hex = публичный идентификатор, не секрет |

## Что случилось

`check_secrets` давал `rc=1` на **5** строках в архивных чатах. Все 5 — hex-строки:
2 git-коммита, 2 git blob/tree, 1 sha256-дайджест DLL. Реальный пароль (`TE-052`) @TE зачистил
отдельно. То есть гейт красный на **публичных идентификаторах**, а не на секретах.

## Причина

`SHAPES` содержит правило `hex-long` — `\b[0-9a-fA-F]{32,}\b`: красит **любой** hex длиной 32+,
без проверки «это объект git или дайджест?». git-SHA (40 hex) и sha256 (64 hex) по форме
совпадают с «длинным hex», хотя по смыслу это идентификаторы/дайджесты, а не значения.

## Фикс

В `scan_text` для `hex-long` добавлена проверка `_hex_is_identifier`:
- 40-hex → `git cat-file -e <hex>` → объект есть ⇒ **не секрет**;
- 64-hex → sha256-дайджест ⇒ **не секрет**.

Плюс селфтест-кейсы: git-коммит (HEAD) → 0 находок; sha256 → 0 находок; фейковый ключ → ≥1.

## Проверка (двусторонняя, §5.4)

- дефект: 5 hex-находок → после фикса `rc=0`;
- норма: фейковый ключ `Xk3Jd9…=` и `assign:password` → по-прежнему ловятся.

## Почему важно документировать

Это второй дефект `hex`-класса за неделю (первый — `base64-long` ловил цепочку идентификаторов,
дефект 2026-11-10). Правило: **каждый ложный красный гейта фиксируется кейсом AN-xx** (что,
причина, фикс, проверка), чтобы не «чинить по одному» и видеть, что класс повторяется.
