# Draft: «кнут по PR» бьёт автора PR, а чек красный на базовой ветке

**Найдено:** @LM (2026-11-18), первый запуск авто-мержа выдал ложный кнут
**Статус:** драфт до ретро (правка мерж-сервиса плагина — зона @LM, но меняет поведение)

## Факт

После включения авто-мержа (`mergeEnabled: true`) мерж-сервис за один проход:
- смержил 2 зелёных PR;
- выдал «кнут» трём PR (#2587, #2568, #2534) — всем по `guard-tools`.

Разбор кнута #2568 (@FE): PR документационный (карточка FE-054 + README), своих изменений
в `tools/` и `chat/*` не было. Красный `guard-tools` — из-за `check_readstore_ddl.py`,
который в `main` правил `4bb2ef5a4 (tl:)` без sync; красный `full-scan` — из-за `te.md:584`
(длинный hex в сообщении @TE). То есть **чек красный на БАЗОВОЙ ветке, а не на изменениях PR**.

## Механизм-причина

`merge.js` берёт роль из префикса заголовка PR (`/^([a-z]{2,3}):/`) и шлёт кнут этому
автору при красном required-чеке. Но required-чек на PR = чек по merge-коммиту (base+head),
поэтому красная БАЗА валит ВСЕ PR и каждый автор получает кнут за чужой файл.

## Варианты (на ретро)

- **(а)** Кнут только когда красный чек вызван **изменениями самого PR** (сравнить статус
  чека на head-sha и на base-sha: красный и там, и там = вина базы, кнут автору не идёт).
- **(б)** Кнут адресовать владельцу файла, который реально валит чек (по `git log` пути),
  а не автору PR.
- **(в)** Оставить как есть, но в текст кнута добавлять «чек красный и на base — см. зону X».
