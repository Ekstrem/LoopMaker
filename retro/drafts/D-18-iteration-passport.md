# D-18. Итерация как эксперимент: паспорт генерации и чистые входы bounded context

| Поле | Значение |
|---|---|
| **Статус** | черновик |
| **Автор** | владелец (цель) + @LM (формулировка) |
| **Затронет** | @AR (входы), @BE (генерация сервисов), @TL (приоритеты), @LM (паспорт/метрики) |
| **Дата** | 2026-11-08 |

## Контекст

**Продукт нужен по-настоящему:** владелец пользуется платными аналогами с более скромной
функциональностью, и XDiary должен их заменить. Поэтому приоритет — работающее приложение,
и любые процессные улучшения оправданы только если они **ускоряют и стабилизируют** доставку.

Параллельно у владельца есть **вторая, непубличная цель**: итерации дают материал для оценки
**воспроизводимости генерации** сервисов по ограниченным контекстам. Из этой цели следуют
требования к **чистоте и повторяемости** входов/выходов, но **сама цель команде не транслируется**
(знает только @AR). Для команды те же требования формулируются на своих основаниях:
качество контрактов, воспроизводимость, меньше ручных проверок — это полезно и без второй цели.

Следствие для процесса: итерация должна иметь воспроизводимые входы, зафиксированный выход
и сравнение с предыдущим прогоном. Иначе «сгенерировали и вроде работает» — не измерение,
но и для продукта это означает «нечем доказать, что стало лучше».

**Три разрыва, которые прямо бьют по цели:**

1. **Вход есть, но имена не унифицированы:** `BC-Client` использует
   `01-bounded-context-canvas.md`, остальные 10 — `01-context-canvas.md`. Артефакт на месте,
   но **поиск по имени** (а генератор ищет именно так) пропустит этот контекст. Это дешевле
   чинить сейчас (переименовать или сделать алиас), чем ловить «почему генератор не увидел Client».
2. **Выход не сравним:** нет контракта (OpenAPI), с которым можно сверить сгенерированный сервис.
   Значит «качество генерации» будет оцениваться глазами, а не диффом.
3. **Проверка не покрывает:** 2 из 11 сервисов без тестов — генерация по ним не проверяется
   автоматически (PDR-19 это адресует, но задачи P2).

## Предложение: паспорт итерации

На каждую итерацию — один файл (в `LoopMaker/retro/` или проекте, решит ретро).
Для команды это «журнал итерации», приватная часть (оценка воспроизводимости) — только у владельца
и @AR:

```
iteration: 2026-11-XX
input:     03-ddd/BC-*/01..05 (git SHA) + ADR-0NN (SHA)
command:   как сгенерировали/собрали (скил/промпт/скрипт + параметры) — приватно, если касается оценки
output:    git SHA кода + контракт (OpenAPI, ADR-023)
checks:    build ✓/✗ | tests N/N | контракт ✓/✗ | ручные замечания
diff:      что изменилось против прошлой итерации (структура/классы/эндпоинты)
verdict:   что оцениваем (структура? качество? воспроизводимость?)
```

**Минимум для сравнимости:** один и тот же вход → два прогона → **одинаковый выход**
(детерминизм). Если выход плавает — оценивать нечего, это шум.

**Контракт как общая точка:** либо генерация **spec-first** (OpenAPI → код), либо генерировать
OpenAPI из кода и сравнивать с эталоном. Иначе «код сгенерирован правильно» — вопрос вкуса.

## Что предлагается сделать (кандидаты, не нормы)

1. **Унифицировать имена canvas** (`01-context-canvas.md` во всех 11) — зона @AR, ~10 минут;
   это вход генерации, и он должен находиться по одному правилу.
2. **Ввести паспорт итерации** — 10 строк на итерацию, заполняется @LM по результатам.
3. **Контракт:** решить на ретро, spec-first или code-first (влияет на то, что считается «выходом»).
4. **Детерминизм:** прогон генерации дважды, сравнение хешей (это и есть проверка скила, а не фичи).
5. **Ограничить шум:** итерации генерации проводить в отдельной ветке/worktree, без процесса
   (rebase-инциденты, формат чата, счётчики) — они съедают время, но к оценке скила отношения
   не имеют.

## Что мешает принять сейчас

Правило процесса — до ретро не вводим; плюс решение «spec-first или code-first» — за @AR, а
приоритет (чинить ли `BC-Client` до следующей итерации) — за владельцем.
