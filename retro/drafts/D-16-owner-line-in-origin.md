# D-16. Строка владельца обязана оказаться в `origin`

| Поле | Значение |
|---|---|
| **Статус** | черновик |
| **Автор** | @DO (нашёл), @LM (оформил, добавил свой случай) |
| **Затронет** | @LM (мост/липтеры), @DO (sweep/health), владелец (его outbox `chat/ex.md`) |
| **Дата** | 2026-11-08 |

## Проблема

За сутки **дважды** строки владельца существовали только в **рабочем дереве** и отсутствовали
в `origin`: `08:49/08:52/08:53` и `10:21`. Восстановлены позже вручную (`91ab652f`, `86a38c9a`).
Одна из них содержала **живой OTP-код и номер** — @DO зачистил перед коммитом (§6).

Тот же класс — **мой собственный случай** (14:11/14:46): два решения лежали в дереве без коммита
и исчезли при синхронизации; восстановлены через 40 минут.

Причина одна: **запись в файл ≠ запись в git**. Мост/агент кладёт строку в `chat/ex.md`
(или `chat/lm.md`), но коммит делает человек/роль позже. Любой `reset`/`checkout`/чужой
`merge` — и строки нет ни у кого.

## Предложение

1. **Проверка «в дереве нет несохранённых строк чата»:** `git status --porcelain
   5-tech-backlog/chat/*.md` непустой → предупреждение в `sweep`/`health` (или
   `chat_lint --check-dirty`) с именами файлов и N строк.
2. **Проверка «каждая строка `ex.md` есть в `origin»:** для каждой строки-сообщения локального
   `ex.md` проверить наличие в `git show origin/main:5-tech-backlog/chat/ex.md`; отсутствует →
   дефект моста (не «опоздание»).
3. **SLA публикации:** строка владельца должна быть в `origin` в пределах **10 минут** (иначе —
   сигнал в чат и в `health`).
4. **Секреты владельца:** если строка содержит код/номер — в коммит она попадает **зачищенной**
   (§6); проверка: regex OTP/телефона в diff перед коммитом, замена на `<код вырезан>`.

## Цена

~25 строк (проверка 1–2) + строка в `health`; риск ложных срабатываний: файл только что изменён
агентом и ещё не закоммичен — порог 10 минут снимает.

## Как проверить

- `--check-dirty` на дереве с незакоммиченной строкой → **rc=1**; после коммита → 0;
- негативный контроль (D-12): удалить строку из `origin`-копии → проверка 2 краснеет;
- инцидент «строка владельца потерялась» — 0 за итерацию.

## Что мешает принять сейчас

Правило до ретро не вводим; плюс неясно, кто коммитит: мост (плагин) не должен делать git-операции
сам (общий дерево, rebase-состояния) — вероятно, коммит должен делать `sweep`/`health`-раннер
или агент, прочитавший строку.

- @LM — свой случай: два решения (14:11/14:46) потеряны без коммита, восстановлены через 40 минут.

## Реализовано @DO (19:30) — `tools/check_owner_chat.py`

Инструмент реализует все четыре пункта и **проверен негативным контролем**: тестовая строка со
старым штампом и кодом → «грязные файлы чата (1)», «строка отсутствует в origin и старше 10 мин»,
«§6: есть код/номер», **rc=1**; после проверки файл восстановлен, дерево чистое.
На текущем состоянии: `строк локально 11, в origin 11, отсутствуют 0` → rc=0 (проверено мной).

### Куда подключать: **только локально, не в CI**

На GitHub-раннере дерево **всегда чистое** (свежий checkout), поэтому `git status --porcelain` пуст,
а `ex.md` совпадает с origin — то есть в CI этот гейт **всегда зелёный**. Это ровно класс D-12/D-14
(«гейт, который не может покраснеть»), ставить его в workflow бессмысленно и вредно: он даст
ложное чувство проверки.

Рабочие точки подключения (обе — в общем дереве, локально):

1. **`git_sync` после пуша** — рядом с существующей проверкой `rev-list --count origin/main..HEAD`:
   пушащая роль сразу узнаёт, что её строка не доехала;
2. **`sweep`/`health`, но только при локальном запуске** — как «детектор» для координатора.

**Коммит строки — по-прежнему за раннером/агентом**, не за плагином моста (git-операции в общем
дереве — источник STOP-инцидентов).
