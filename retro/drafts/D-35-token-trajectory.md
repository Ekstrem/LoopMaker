# D-35. Траектория агентов и бюджет токенов

| Поле | Значение |
|---|---|
| **Статус** | черновик |
| **Автор** | @LM |
| **Затронет** | все роли; DSH session logs, `dsh-loopmaker`, дашборд/метрики |
| **Дата** | 2026-11-25 |

## 1. Вопрос и границы

Оцениваем не «сколько текста написано», а сколько provider-reported токенов проходит
через сессии ролей на пути к артефакту: свежий input, cache read/write и output —
раздельно. Это не денежный отчёт: цены провайдеров здесь не подставляются.

Не ослабляем sandbox, required-чеки, тесты, квитанции обязательств и правило видимого
плана ради экономии. Не считаем перевод на другую модель сокращением числа токенов:
это отдельное решение о цене/качестве.

## 2. Метод и качество данных

- Источник: durable session log v4 DSH `0.2.2-rc.5`, только рабочая область XDiary.
- Используются `assistant/message` / `assistant/attempt`; последний sample одной
  `turn + step` заменяет прежний, `llm/retry-started` открывает новую billed attempt.
  Это соответствует `dsh-token-meter/src/usage-projection.ts`.
- Символьные оценки (`chars / 4`) используются только для chat/tool-трафика и не
  подмешиваются в provider-reported суммы. Для русского текста и JSON такая эвристика
  груба; выводы по стоимости из неё не делаются.
- «Ход без tool call» и «chat-only» — сигналы для ручной классификации, а не доказательство
  бесполезности: финальный ответ, решение или ревью могут не требовать инструментов.
- Токены/закрытая задача не публикуем без прямой связи сессии с задачей. Общее число
  закрытых карточек за историю репозитория нельзя делить на токены выбранных сессий.

Git добавляет транспортный шум: `chat(bot): sync` = 860 из 13 141 коммитов (6,5%),
а за последние семь дней снимка — 98 из 484 (20,2%). Коммиты сами по себе не равны
модельным ходам, поэтому это отдельный сигнал, а не слагаемое token usage.

Вывод по траектории: роль часто не двигается «задача → артефакт → ревью», а заново
объясняет промежуточное состояние гейта/транспорта всем заинтересованным. Самый
дешёвый путь — канонический живой checklist задачи + одно изменение состояния +
ссылка на доказательство, а не повторный рассказ всей цепочки.

Ограничение классификатора: status/review сообщения нельзя автоматически считать шумом —
они содержат 48,2% символов, но во многих есть реальные доказательства. Отсекаем только
повтор одинакового состояния и обязательную конечную строку ревьюеру сохраняем.

## 5. Уже существующие ограничения и решения

- PDR-041: постоянный фильтр-субагент припаркован — его собственный расход дороже
  проверяемой пустоты. Новый LLM-фильтр не предлагаем.
- Статус-строки и ack-ack уже не нужны; дедуп кнута по PR + head SHA + чек уже есть.
- Текущий `notifyStyle: pointer` не содержит диапазона строк: адресат получает файл и
  метку, после чего может прочитать лишнее. Гибрид «короткое действие — copy,
  длинное/пакет — точечный pointer» требует замера до внедрения.
- В профиле нет явной политики компакции. Компакция срабатывала (142 раза), но
  медианное pressure ~442k говорит, что рабочий контекст всё равно велик; настроить
  порог/retention по маршруту — вопрос замера, не молчаливой правки.
- Замер provider usage показал: **расход ≈ число шагов × давление контекста**
  (99,2% — cache read перечитываемого контекста). Поэтому экономия делится на два
  рычага: (1) меньше контекста на шаг, (2) меньше шагов. Подавление ack-ходов
  почти ничего не даёт (0,5% total) — на это не тратим усилия.

## 6. Предложения

Приоритет по замеру: **(1) давление контекста на шаг** — треды живут месяц при
медиане ~442k; **(2) число шагов** — каждое пробуждение/перепроверка стоит ~440k
prompt-токенов; **(3) содержание чата** — влияет на оба, потому что чат лежит
внутри контекста роли. Подавление ack-ходов и точная дедупликация — не рычаги
(0,5% и <0,5% соответственно).

### P0. Сначала локальный token ledger, без агента

Собирать суточный агрегат из DSH-журналов: по роли/модели — свежий input, cache
read/write, output, попытки, `no-tool`/`chat-only` ходы, компакции, p50/p95 prompt
pressure. Это не GitHub health: журналы живут локально, поэтому сборщик — локальная
задача, а в git попадают только обезличенные агрегаты приватного LoopMaker.

**Эффект:** прямой экономии нет; она появляется только при следующих мерах.
**Приёмка:** отчёт воспроизводится без LLM и не содержит текст сообщений/секретов.

### P1. Батчировать обычные пробуждения, критические не задерживать

Сейчас `batchWindowMs = 8000`. Пилот: обычные уведомления копятся 60 с; raw/явно
критические идут сразу. Это не LLM-фильтр и не удаление сообщений: меняется только
число модельных пробуждений на пачку. Обязательные квитанции и вопросы не отменяются.

**Цель пилота:** на 30% меньше ходов-доставок при том же числе сообщений;
`missed_critical = 0`, задержка обычных ≤ 60 с. При любом пропущенном крите — откат.
Это цель/порог отката, а не заранее обещанная экономия.

### P1. Заменить «pointer → прочитай весь outbox» на гибрид

- одно короткое действие доставлять как `copy`, без второго tool round-trip;
- длинный текст/пакет доставлять pointer с `file + line range` либо инструментом
  unread-дельты из `seen`, а не чтением файла целиком;
- исторический файл остаётся источником правды, текст не редактируется.

**Приёмка:** node-тесты на короткое/длинное/пакет и точный диапазон; по журналу —
не менее 80% меньше строк, читаемых на одну доставку, при `missed_critical = 0`.
Выбор между copy и pointer делается по измеренной длине, а не новым агентом.

### P1. Не будить всех там, где нет работы для каждой роли

`@all` остаётся для действительно общего обязательного изменения. Информационные
рассылки идут в дайджест и читаются по требованию; прямой `→ @роль` остаётся для
действия/вопроса. Не требовать «подтверди получение» на информационные сообщения.

**Приёмка:** fan-out измеряется как число модельных ходов всех адресатов, а не число
строк в git; цель пилота — на 50% меньше ходов на broadcast без поздних критов.

### P1. Сначала FE/DO: дайджест + ссылка вместо длинной реплики

Замер даёт самый конкретный резерв: 97,0% символов длинных сообщений принадлежит
FE и DO. Для сообщения ≥1000 символов в чате остаются до 200 символов: сигнатура
дефекта, изменившееся состояние, кто должен действовать, ссылка на карточку/run.
Матрица тестов, diff и полный лог живут в артефакте, а не в чате.

Для FE-054/BE-128/BE-131/Garmin вводится один живой checklist в карточке: повторное
промежуточное «гейт всё ещё идёт» не отправляется. Обязательная конечная строка
ревьюеру сохраняется.

**Оценка:** правило дайджеста на текущем снимке сняло бы 16,9% chat-объёма
(символьная оценка, не provider total). **Приёмка:** p95 длины FE/DO и output tokens
на chat-only ход падают; полнота решения проверяется по карточке. Длинный разбор не
запрещаем жёстко, если он сам и есть необходимый артефакт.

### P1. Пересоздавать тред на границе итерации/задачи при большом контексте

Крупнейший одиночный рычаг по замеру: медианное pressure ~442k при шагах в
десятках тысяч означает, что месяц жизни треда перечитывается на каждом шаге.
Один активный тред на роль сохраняется, но после мержа и при высоком
`projectedTokens` владелец открывает свежий тред с коротким bootstrap: роль,
текущая карточка, последний commit/PR, следующий гейт. Не делаем это посреди
задачи.

**Приёмка:** меньше компакций и prompt pressure на новую задачу; нет потерянных
зависимостей/статусов. Сброс ради самого сброса запрещён: он ломает тёплый cache.

### Что сознательно не предлагаем

- Постоянный LLM-фильтр сообщений — PDR-041 уже показал отрицательную экономику.
- Подавление ack/no-tool ходов: замер показал 0,5% total — усилия не окупаются.
- Отключить гейты/тесты, ослабить sandbox или убрать видимый план.
- Менять `maxTokens`/порог компакции до измерения её частоты и cache-последствий.
- Считать субагентов экономией по умолчанию: они изолируют контекст, но могут
  увеличить суммарный расход; для телеметрии нужен скрипт, не ещё одна роль.

## 7. Цена и риски

- Метрики собираются локальным скриптом без модельного вызова; в отчёт не попадают
  тела сообщений, аргументы с секретами или содержимое tool results.
- Подавление пробуждений рискует задержать критическое сообщение. Любой пилот имеет
  `missed_critical = 0` как условие отката; обязательные квитанции не подавляются.
- Смена компакции или сброс треда меняет KV-cache и может увеличить свежий input.
  Поэтому такие меры — только эксперимент с замером до/после, не немедленная норма.

## 8. Как проверить

- Повторяемый отчёт строится без LLM; usage fold проходит synthetic fixture:
  replacement внутри step, retry, отсутствие usage и отсутствие текста в выводе.
- Эффект считаем по той же выборке/окну: свежий input, cache read/write, output,
  `no-tool` и `chat-only` доли, компакции и merged PR за период.
- Для новой живой метрики в `METRICS.md` кандидат — `token_efficiency`; место освобождаем
  за счёт припаркованной `closure_gap`, а не раздуваем реестр.
