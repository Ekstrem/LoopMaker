## Проблема

Три гейта за сутки были **зелёными при дефектах**, и каждый раз это выяснялось случайно:

1. `front-e2e-repeat` — `continue-on-error: true` + `|| true`: джоба зелёная при падениях,
   «success» ничего не значил (исправлено: `::error` + exit 1 в итоговом шаге);
2. `stats --check` — сверял README с **рабочим деревом**, а не с `origin`: «актуален», когда
   правка не запушена (исправлено: `--check --ref origin/main`);
3. прогон **#7** — шаг очистки вымыл засеянные карточки **до** тестов: мерили чистый стенд
   и собирались отчитаться «0 падений на грязном» (исправлено: вход `cleanup: yes|no`,
   в `#8` шаг `skipped`).

Плюс `stats.py` не видел папку `tl/` (дефект покрытия) — и при этом `--check` был **зелёным**.

## Предложение

Новый гейт принимается только вместе с **негативным контролем**: доказательством, что он
**умеет** краснеть на реальном дефекте. Не «мы уверены», а «вот прогон, где он красный».

- для линтера — тест «плохой вход → rc=1»;
- для проверки согласованности — сверка с **источником**, а не с кэшем/деревом, и пример
  реального расхождения (`--check --ref` на истории дал **7 из 14** коммитов rc=1);
- для гейта-«наблюдателя» — шаг, который падает, если данных нет (`::error`, `exit 1`).

## Цена

Один негативный контроль на гейт (обычно 10–20 строк теста). Риск: гейт без контроля
не принимается — «пока не готово» становится нормой для недоделанных гейтов.

## Как проверить

- у каждого гейта в `RULES.md`/`docs/CI-RULES.md` есть ссылка на негативный контроль
  (коммит/прогон);
- число случаев «гейт зелёный при дефекте» за итерацию — **0**.

## Что мешает принять сейчас

Правило процесса — до ретро не вводим. Плюс нужен мета-гейт: как проверять, что у гейта есть
контроль (пока это ручная сверка по чек-листу в `RULES.md` §18).
