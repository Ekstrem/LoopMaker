# Плагин `dsh-loopmaker` — мост «чат петли → сессия роли»

Проблема, которую он решает: чат ролей лежит файлами, и чтобы BackEnd узнал
о сообщении от FE, его тред надо открыть и разбудить руками. Плагин делает это сам:
находит в outbox'е строку `- [ts] → @FE: текст`, определяет по заголовку сессию FE и
кладёт в неё сообщение — тред просыпается и продолжает работу.

```
5-tech-backlog/chat/be.md
  - [2026-11-01 10:00] → @FE: посмотри контракт JWT
            │
            ▼  плагин (poll раз в 5 с)
   сессия «XDairy | FrontEnd»
   сообщение от BackEnd: «посмотри контракт JWT»
```

## Установка

```powershell
dsh plugin --profile desktop add github:Ekstrem/LoopMaker
```

Добавить бандл в `~/.dsh/profiles/desktop/package.json`:

```json
"dsh": {
  "profile": {
    "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "dsh-loopmaker"]
  }
}
```

Для разработки вместо GitHub — локальный путь: `dsh plugin --profile desktop add file:C:\...\LoopMaker`.

## Настройка

Бандл-патч ([cordis.patch.yml](cordis.patch.yml)) монтирует запись `loop-chat` с дефолтами.
Свои значения — в профильном `~/.dsh/profiles/desktop/cordis.patch.yml`, по `id`:

```yaml
- id: loop-chat
  config:
    chatDir: C:\Users\About\Documents\GitHub\XDiary\5-tech-backlog\chat
    project: XDairy
    titleTemplate: "{project} | {role}"
    roles:
      be: BackEnd
      fe: FrontEnd
      do: DevOps
      te: TestEngineer
      ar: Architect
      tl: TechLead
      po: PO
```

| Параметр | Смысл |
|---|---|
| `chatDir` | папка outbox-чата; **абсолютный путь надёжнее** (относительный раскрывается от `workspaceRoot` или cwd процесса) |
| `workspaceRoot` | база для относительного `chatDir` |
| `project` + `titleTemplate` | как из роли получается заголовок сессии: `{project}`, `{role}`, `{code}` |
| `roles` | файл чата → название роли (`be: BackEnd`) или `{ title, tag }` для нестандартного тега |
| `sessions` | жёсткое переопределение: `{ fe: "XDairy | FrontEnd" }` — если заголовок не по шаблону |
| `messageTemplate` | что видит адресат: `{from}`, `{to}`, `{code}`, `{text}`, `{ts}`, `{file}` |
| `notifyStyle` | `copy` — с текстом сообщения; `pointer` — только «в чате <файл> есть сообщение от X» |
| `pointerTemplate`, `pointerBatchTemplate` | шаблоны указателя: `{files}`, `{from}`, `{count}`, `{ts}` |
| `history` | `skip` (по умолчанию) — на первом запуске не доставлять историю; `deliver` — доставить всё |
| `pollMs` | период опроса, по умолчанию 5000 |
| `broadcast` | рассылать `@ALL` всем, кроме автора (по умолчанию выключено — иначе одно сообщение будит все треды) |
| `dryRun` | только логировать доставку, ничего не отправляя (безопасный первый запуск) |
| `logFile` | дублировать лог моста в файл (у DSH нет своего лог-файла) |
| `stateFile` | где хранить `seen`/`pending`; по умолчанию `$DSH_HOME/loopmaker-chat-state.json` |
| `pendingTtlMs`, `maxAttempts` | сколько ждать недоставленное сообщение и сколько раз пытаться (TTL держите больше `freezeMs`) |
| `batchWindowMs` | дебаунс: сколько ждать «успокоения» пачки перед отправкой (0 — сразу) |
| `batchHeader` | заголовок склеенной пачки (`{count}`, `{from}`, `{to}`) |
| `maxHops`, `hopWindowMs` | сколько раз одна пара «A → B» может доставить за окно (по умолчанию 4 за 30 мин) |
| `maxPerHour` | потолок входящих реплик роли за час (по умолчанию 40) |
| `escalateTo` | кому передаётся переписка после порога (по умолчанию `tl`) |
| `escalationTemplate` | текст эскалации: `{from}`, `{to}`, `{reason}`, `{count}`, `{messages}` |
| `freezeMs` | сколько пара остаётся замороженной после эскалации (по умолчанию 1 час) |

## Как ищется сессия

1. Роль из имени файла: `be.md` → `be`.
2. Ожидаемый заголовок: `sessions[role]` или `titleTemplate` (`XDairy | BackEnd`).
3. Сравнение с заголовками сессий: точное совпадение → вхождение → самая свежая.
   Регистр, `ё`, кавычки и лишние пробелы не важны.
4. Архивные и субагентские сессии игнорируются — писать в них нельзя.

**Адресат перепроверяется перед каждой отправкой.** Мост помнит id последней сессии
роли, но перед доставкой сверяет его с живым списком:

- сессия жива → пишем в неё, даже если тред переименовали (имя не важно, id стабилен);
- сессии нет в живых (уехала в архив) → ищем по имени и **переключаемся на новую**,
  в лог уходит `таргет переехал <old> → <new>`;
- замены ещё нет → сообщение ждёт в очереди, а не уходит в архив.

Так смена треда (архив старого, новый с тем же именем) не теряет сообщения и не требует
правки конфига — совпадения по имени достаточно.

## Тормоза: чтобы петля не звенела

Переписка «роль ↔ роль» легко превращается в пинг-понг по одному сообщению. Мост
ограничивает это тремя независимыми механизмами.

**1. Пачка вместо строчки.** Все сообщения одному адресату за проход уходят **одной**
репликой (заголовок + список). Плюс `batchWindowMs` — дебаунс: пачка ждёт «успокоения»,
чтобы всплеск из пяти строк не стал пятью ходами:

```
сообщения из чата петли (2, последнее от BackEnd):
- [2026-11-01 12:00] BackEnd: переделал контракт
- [2026-11-01 12:01] BackEnd: и поправил тесты
```

**2. Лимит кругов пары.** Для каждой пары «A → B» считаются доставки за `hopWindowMs`
(по умолчанию 4 за 30 минут). На превышении доставка **останавливается**, а сообщения
уходят координатору.

**3. Бюджет роли.** Не больше `maxPerHour` входящих реплик на роль за час — страховка от
рассылки по кругу через третьих лиц.

### Эскалация: кто разбирает

Порог достигнут → формируется одно сообщение координатору (`escalateTo`, по умолчанию
TechLead), исходные строки из очереди снимаются, пара замораживается на `freezeMs`.
Уведомление — **указатель, а не пересказ**: переписка остаётся в чате, координатор
читает её сам, и текст не расходится с файлом.

```
LoopMaker: в чате есть переписка BackEnd ↔ FrontEnd — превышен лимит (4 кругов за 30 мин).
Смотри be.md, fe.md (последнее сообщение 12:01). Разберись, пожалуйста: техническое —
реши сам, бизнесовое — передай PO, архитектурное — AR.
```

Если всё же нужен дамп переписки внутри уведомления — в `escalationTemplate` есть
`{messages}`: подставьте его в шаблон, и тексты вернутся.

Классификацию «техническое/бизнесовое/архитектурное» делает координатор — у него для этого
есть задачи и чат. Плагин лишь гарантирует, что после порога решение принимает человек,
а не две роли, спорящие по кругу.

### Что видит адресат: копия или указатель

| `notifyStyle` | Что приходит в сессию |
|---|---|
| `copy` (по умолчанию) | `сообщение от BackEnd: «переделал контракт»` — текст внутри |
| `pointer` | `в чате be.md есть сообщение от BackEnd (12:01) — посмотри файл` |

`pointer` экономит контекст треда и исключает расхождение «в сообщении одно, в файле
другое»: роль читает файл-источник сама. Шаблоны — `pointerTemplate` (одно сообщение)
и `pointerBatchTemplate` (пачка), доступны `{files}`, `{from}`, `{count}`, `{ts}`, `{to}`.


Если подходящей сессии нет, сообщение **не теряется**: оно лежит в очереди (`pending`)
и доставляется, когда сессия появится (открыли, переименовали) — до `pendingTtlMs`.

## Что важно знать

- **Оживление = новый ход.** Сообщение уходит как пользовательское (`source.kind: user`),
  поэтому сессия не только получает текст, но и начинает работу. Это осознанно: иначе
  роль просто «прочитает» сообщение и промолчит.
- **История не дублируется.** Ключ сообщения — файл + время + адресат + хеш текста;
  состояние переживает перезапуск DSH. Первый запуск с `history: skip` помечает
  существующие строки просмотренными, не будя никого.
- **Своё сообщение себе не отправляется** (`@BE` из `be.md` — заметка, не письмо).
- **Плагин ничего не пишет в чат** и не создаёт сессии: только доставляет в существующие.
- **Файлы чата могут быть с BOM** — парсер его снимает (Windows-редакторы любят BOM).

## Диагностика

| В логе | Что делать |
|---|---|
| `chatDir не задан — мост выключен` | задать `chatDir` в профильном патче |
| `папка чата недоступна` | проверить путь; относительный раскрывается от `workspaceRoot`/cwd |
| `сессия «XDairy | FrontEnd» не найдена` | сверить заголовок треда в списке DSH; при несовпадении — `sessions: { fe: "<точно как в списке>" }` |
| `роль fe: таргет переехал old → new` | старый тред в архиве, мост переключился на живой с тем же именем; действий не нужно |
| `роль fe: … замена ещё не появилась` | архив без замены: создайте тред `XDairy | FrontEnd` — сообщения дождутся |
| `→ fe: сообщение…` | доставлено (в `dryRun` — только запись в лог) |
| `BackEnd ↔ FrontEnd: N кругов за M мин — передано координатору` | сработал порог: разбор у TechLead, пара заморожена |
| `пара be->fe заморожена` | идёт разбор, после `freezeMs` доставка вернётся сама |
| `сообщение для fe устарело` | сессия так и не появилась за `pendingTtlMs` |

## Проверка

```bash
npm test        # 37 тестов: парсер, поиск и ретаргет сессии, батчинг, лимиты, эскалация
```

Тесты не требуют DSH: маршрутизация проверяется на фейковых сессиях и отправке.
В среде, где нельзя порождать процессы, запускайте так:
`node --test --test-isolation=none "test/*.test.mjs"`.

## Структура

```
package.json           пакет плагина (main -> lib/index.js)
cordis.patch.yml       бандл-патч с дефолтной записью loop-chat
lib/index.js           Config/inject/apply: сервисы, агент, followup
lib/bridge.js          проход: файлы -> сообщения -> очередь -> доставка
lib/parse.js           разбор строки чата, BOM, ключ сообщения
lib/state.js           seen/pending, атомарная запись
lib/sessions.js        заголовки сессий, мягкое сравнение
lib/config.js          нормализация конфига, шаблоны
test/                  node:test
```
